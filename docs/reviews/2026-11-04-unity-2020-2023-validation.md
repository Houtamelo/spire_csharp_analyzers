### What the 82 failures mean

**67: Unity assembly discovery stops before generator execution.**
`UnityGeneratorTestHarness.AssertUnityAssembliesAvailable` unconditionally
requires `Editor/Data/Managed/UnityEngine/Unity.Scripting.dll`. That file is absent
in the tested 2023 installation. The affected tests include serialization
attributes, generated drawers, field collisions, payload accessors, and snapshots,
but their failure messages all originate from this same precondition. They do
not establish 67 broken generator behaviors. The harness must locate the actual
assemblies defining its required types for each supported Editor, then run every
affected assertion. Simply removing the precondition would not verify those cases.

**3: executable test code was compiled against the wrong framework references.**
`ExistingToStringFormattingIsPreserved` fails to resolve
`System.Runtime.CompilerServices.DefaultInterpolatedStringHandler` in
`System.Runtime, Version=8.0.0.0`. `SharedManagedTuplePayloadsRoundTripAndBoxOnlySharedStorage`
and `TypedEquivalentTuplesReuseSlotsButPreserveSimultaneousOccupancy` fail to
resolve `System.ValueTuple<T1, T2>` from that same assembly identity. The harness copies
.NET 8 reference assemblies for semantic tests; on this older host, its runtime
compilation fallback also selects those references. Unity 2023's Mono runtime
cannot execute all IL produced against that contract. This does not mean Unity
lacks tuple support. Executable test compilations need references matching the
actual Unity runtime; pure semantic analysis can retain a separate reference set.

**3: JSON reference/converter tests require a focused follow-up.**
`JsonNamesWithQuotesEscapesAndControlsCompileAndRoundTrip` and
`GlobalJsonDiscriminatorWithQuotesEscapesAndControlsCompilesAndRoundTrips` both
stop on `SPIRE_DU006` (System.Text.Json not referenced). The third,
`GlobalJsonDefaultAndExplicitNoneControlConverterEmission`, cannot find the
expected `.Stj.g.cs` converter output. These helpers append the runtime
System.Text.Json DLL to framework references that already contain a different
System.Text.Json reference; their comparer deduplicates paths, not assembly
identities. An ambiguous/mixed reference set is a likely shared cause, inferred
from source and saved inputs, but not yet confirmed by an isolated rerun.
These failures cannot yet be dismissed as harness-only or called three JSON
round-trip corruptions: two stop before a round trip, and one checks emission.

**8: existing packaging/fixture failures also occur in the normal .NET run.**
Five assertions report the same missing showcase `Editor/csc.rsp` and/or its
`.meta` file. The authored response file enables nullable analysis and C# 10;
the sample allowlist omits it. These are package-content failures, not evidence
of a Unity 2023 compiler regression. One assertion still requires the old README
phrase "Rider is the supported IDE"; the documentation now says "verified IDE
workflow." Another finds a broken packaged link from `Reference/rules/SPIRE009.md`
to an issue document that is not shipped at that destination. The last assumes a
pre-existing `tmp/unity-asmdefs/Library/Bee` fixture. The README/Bee checks need
updated expectations/setup; the missing sample files and broken link affect
customer-facing package contents and should be repaired before release.

**1: the async test adapter fails, rather than reporting an analyzer mismatch.**
The recorded case is
`Houtamelo.Spire.GlobalConfig.EndToEnd.EnumExhaustivenessTests.SwitchStatement_ExhaustiveOnUnmarkedEnum`.
Its exception is `EditMode test can only yield null`, from Unity Test Framework
execution. There is no expected-vs-actual exhaustiveness diagnostic in this
failure. It also explains the XML root's off-by-one failure count. The separate
behavioral launch records the same runner exception on a different case,
`RecordTests.TypePatternMatching`; the exact scheduling/coroutine defect remains
unlocalized. The harness/runner needs correction and both assertions must be
rerun successfully before acceptance.

The importer metadata defect, general integration assertion, Inspector memory

### Plugin metadata finding

The original metadata serializes the Any-platform entry as an empty key with
value `Any`. Unity 2023's actual `PluginImporter` reports `any=false` and
`linux=false`, even though that entry contains `enabled: 1`. This affects both
`Runtime/Houtamelo.Spire.dll` and the behavioral suite's dependency plugins.

In a disposable project, calling Unity's importer API to enable Any/Linux writes
an additional entry with **`Any` as the key** and an empty value. The importer
then reports `any=true`, `linux=true`; the behavioral player compiles its C# and
reaches the native build. Package DLL bytes remain unchanged. This is diagnostic
normalization of the test copy, not a shipped package metadata fix or a completed
player acceptance result.

## Harness preparation

- ProjectVersion files identify the selected Editor; tracked fixtures are untouched.
- Test-only response files use the installed compiler's supported language mode.
  Unity 2023 needs `preview` for the unchanged raw-string test sources. The
  assembly-definition customer scenarios retain C# 9.
- Disposable native fixtures use `GetInstanceID()` in place of Unity 6's
  `GetEntityId()` for the same object-identity comparisons; `ReferenceEquals`
  assertions remain intact.
- Disposable SDK pins use installed `8.0.319` instead of unavailable `8.0.318`.
- Legacy libxml2/OpenSSL libraries are extracted privately in `native-libs`;
  system libraries are untouched. The OpenSSL package comes from
  [Ubuntu's official archive](https://security.ubuntu.com/ubuntu/pool/main/o/openssl/).
  Unity 2020 also needs a process-local invariant globalization setting.
- Two test diagnostic-formatting helpers now convert diagnostics to strings
  explicitly before `string.Join`. This resolves a .NET Standard overload
  ambiguity without changing assertion conditions.

No analyzer or generator implementation was changed. No failed test was removed,
filtered, marked ignored, or converted to an expected pass.

The initial complete .NET run records **2,668 cases: 2,653 passed, 15 failed**.
Seven failures came from the portable harness's two ambiguous diagnostic-format
calls; after their repair, the DevTools rerun passes 120/128, retaining eight
packaging/fixture failures. Subsequent constrained analyzer and PatternAnalysis
runs pass 926/926 and 428/428. Normal-host generator reruns hit the RSS watchdog,
including a partitioned attempt; completed partitions are retained, but are not
reported as a fresh passing run of all 1,042 cases. The post-fix Unity run does
execute all 1,039 portable generator cases as part of its full identity check.

## Resource incident and subsequent limits

The rendered Inspector validation consumed approximately 19 GB while stalled.
Its timeout was too permissive; it affected host responsiveness. The memory
growth has not been localized to a specific drawer or automation operation.
All owned Unity processes were gone after cleanup, with approximately 22 GiB
available on the host. The graphical test was not restarted.

Subsequent operations run sequentially through `limited_run.py`:

- CPU affinity restricted to logical CPUs 22/23, plus a two-core CPU quota.
- Unity job-worker count 2; .NET processor count 2; MSBuild node reuse disabled.
- Systemd memory maximum 3 GiB, high watermark 2 GiB, swap disabled.
- Independent watchdog kills the scope above 2 GiB aggregate RSS.
- Managed follow-up runs additionally cap each managed heap at 512 MiB and
  request conservative GC; shared compilation is disabled where necessary.

The normalized IL2CPP build was stopped by that watchdog at approximately
2.76 GiB sampled aggregate RSS. This is a resource-limited incomplete run,
not a Spire runtime failure. The same guard stopped follow-up host generator
operations slightly above 2 GiB; their incomplete results are preserved.
Scope logs and `.resources.json` files record the
limits, peak RSS, and termination reason for each constrained operation.
