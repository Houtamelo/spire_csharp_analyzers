# Unity 6000.6.5f1 serialization recheck

The blanket statement that generated Unity serialization is unsupported on
6000.6.5f1 was too broad. The current representation passes native Editor
write/read checks, but generic unions instantiated with reference-type arguments
still reproduce the engine crash. The payload redesign did not remove that path.

All runs used fresh disposable projects, private Xvfb displays, Linux x64, and
the same four package DLLs built from the current working tree. The Editor builds
were 6000.6.5f1 (`3ff58d469c8a`) and 6000.5.6f1 (`0e0577a1a2ac`). No production
implementation or tracked C# fixture was changed for this investigation.

| Check | Editor | Result |
|---|---|---|
| Current variant-payload fixture, Write | 6000.6.5f1 | 126 checks, zero failures; exit 0 |
| Same assets, Read in a fresh process | 6000.6.5f1 | 87 checks, zero failures; exit 0 |
| Full current Unity integration fixture | 6000.6.5f1 | SIGSEGV during asset creation; exit 139, no final report |
| Isolated `UnityGenericUnion<int>` | 6000.6.5f1 | Managed preparation and native save/reload pass; exit 0 |
| Isolated `UnityGenericUnion<string>` | 6000.6.5f1 | Managed preparation passes, then CreateAsset triggers SIGSEGV; exit 139 |
| Identical string probe | 6000.5.6f1 | Managed preparation and native save/reload pass; exit 0 |

The core fixture includes non-generic unions with managed payload fields and
generic unions constrained to unmanaged type arguments. Its passing string
payloads do not test a union whose own generic type argument is `string`.
The isolated probes use separate ScriptableObject classes in matching source
files and differ in their generic argument and test value. This avoids the
separate historical embedded-MonoScript fixture issue.

## Why the redesign does not eliminate the remaining trigger

[UnitySerializationEmitter](../../src/Houtamelo.Spire.Analyzers/SourceGenerators/Emit/UnitySerializationEmitter.cs)
stores the active snapshot in a shared generic class wrapper. The union itself
still implements `ISerializationCallbackReceiver`, and its generated
`OnBeforeSerialize` calls `__SpirePrepareForSerialization`. A union closed over a
reference-type argument therefore still exposes a generic struct callback to
Unity. The new probe verifies that ordinary managed preparation succeeds before
Unity's native asset-serialization invocation crashes.

The [original Spire-free repro and GDB evidence](../issues/unity-6.6-generic-struct-serialization-callback.md)
established the engine-side generic-context failure independently. Unity's
[6000.6.7f1 known issues](https://unity.com/releases/editor/whats-new/6000.6.7f1)
also list a matching generic-struct callback crash,
[UUM-155957](https://issuetracker.unity.com/issues/25665). This is supporting
external evidence; the original submission receipt did not supply an issue ID.

## Unity 7 follow-up, completed November 3

The [Unity 7 comparison](2026-11-03-unity-7-serialization-recheck.md) passes both
the original engine repro and the preserved generic-reference-union probe on
`7000.0.0a12`, including a fresh-process asset read. The same inputs and DLLs
still reproduce the native serialization crash on 6000.6.5f1.

Unity 7 uses CoreCLR in these runs; 6.6 uses Mono. Per the publisher's agreed
decision, issue `25665` is a shared-root-cause working assumption, with its
`7000.0.0a5` fix status publisher-supplied. Exact attribution and the expected
`6000.7.x` backport remain unconfirmed. The measured 6000.6.5f1 limitation still
applies.

## Reproduction and evidence

Core phases use the existing CLI and fixture:

```sh
dotnet run -c Release --project tools/Spire.Tool -- unity-union-core \
  --editor /home/houtamelo/Unity/Hub/Editor/6000.6.5f1/Editor/Unity \
  --project tmp/marketing-serialization-66-recheck-20261102 \
  --method Spire.UnityVariantPayloadCore.SerializedUnionEditorTests.Write --timeout 240
```

Run again with method `Spire.UnityVariantPayloadCore.SerializedUnionEditorTests.Read`
for the fresh-process phase. The isolated probe sources, reports, logs, and
[hash manifest](../../tmp/marketing-serialization-version-recheck-20261102/manifest.json)
are retained in `tmp/marketing-serialization-version-recheck-20261102`.
Copy the two probe sources to `Assets/Editor` in a disposable `unity-integration`
project, then invoke `Spire66IntAsset.Run` or `Spire66ReferenceAsset.Run` with the
same CLI's `--method` option. Use a separate fresh project for the 6.5 control.

The initial sandboxed launch stopped before testing because Unity's global UPM
cache was read-only. The successful reruns had cache access. That setup failure
is not counted as a serialization result. Both crash processes exited on their
own, before their timeout limits.

These checks establish the narrower native Editor boundary, not complete 6.6
Player or rendered Inspector support. The broader release validation baseline
remains 6000.5.6f1. Storefront and customer documentation now name the specific
reference-type generic limitation instead of rejecting all 6.6 serialization.
